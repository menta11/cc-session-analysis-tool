# Claude Code 会话日志数据结构调研

> 调研对象：Claude Code 本机会话日志（JSONL + 同名目录）
> 定位：本目录其它报告（`ccspan-调研报告.md`、`cc-statistics-桌面端重构方案调研报告.md`）偏**工具对比 / 算法借鉴**；本文档是它们的**地基**——系统梳理 Claude Code 会话产物的**数据结构 / 数据字典**，作为自研工具解析层的权威参考。
> 所有结论均用真实会话实测验证（主样本：`71598b9d-…`，90 个 subagent、1572 条记录、跨 2 天）。
> 调研日期：2026-07-30

---

## 0. 一句话结论

**Task / Tool / Subagent 三个维度的耗时，数据全在本机日志里、无需任何埋点**，且有**多个可用的时间源**（轮级 `turn_duration`、工具级 `toolUseResult.durationMs`、子 agent 级 `toolUseResult.totalDurationMs`、以及万能兜底的 timestamp 差值）。坑主要在**覆盖率参差**和**版本差异**——凡是能取的字段都要标注覆盖率，取不到的要能优雅降级到 timestamp 差值。

## 1. 数据存储总览

Claude Code 每个**顶层会话**（一次 `claude` 启动，含 `--resume` 续接）产出：

```
~/.claude/projects/<sanitized-cwd>/<sessionId>.jsonl      ← 主会话日志（每行一个事件）
                                  /<sessionId>/            ← 同名目录（子产物）
                                      subagents/
                                          agent-<id>.jsonl      ← Task/Agent 子 agent 的完整 transcript
                                          agent-<id>.meta.json  ← 子 agent 元信息（类型/任务/嵌套）
                                          workflows/<runId>/    ← Workflow 子 agent（独立 runId 目录）
                                              agent-<id>.jsonl
                                              agent-<id>.meta.json
                                              journal.jsonl
                                      tool-results/
                                          <callId>.txt          ← 大体积工具结果外存（按 id 引用）
```

- `<sanitized-cwd>`：启动时工作目录的编码（`/`、`:`、`\` 等 → `-`）。例：`D:\workspace\process-docs` → `D--workspace-process-docs`。
- 本机根目录：`C:\Users\jlc\.claude\projects\`。
- 实测：历史 **1211 个会话文件含 `isSidechain`**、**173 个含 `subagent_type`**——子 agent 数据覆盖非常充分。

## 2. 主会话 JSONL：记录格式与 type 分布

每行一个 JSON 对象。顶层有 `type` 字段区分记录类型。实测一次会话的 type 分布：

| type | 含义 | 分析价值 |
|------|------|----------|
| `user` | 用户消息 / **工具结果** | 工具结果的主载体（带 `toolUseResult`） |
| `assistant` | AI 回复 | **工具调用的主载体**（`message.content[]` 含 `tool_use` 块） |
| `system` | 系统事件 | **时间数据金矿**：`turn_duration`、`stop_hook_summary` 等（见 §4） |
| `attachment` | 附件/文件快照引用 | 低 |
| `last-prompt` / `mode` / `permission-mode` | 会话元状态 | 低 |
| `ai-title` | AI 生成的会话标题 | 可做会话名 |
| `file-history-snapshot` | 文件历史快照 | 低 |
| `queue-operation` | 队列操作 | 低 |

### 2.1 关键顶层字段总表（`user` / `assistant` 记录）

| 字段 | 出现于 | 用途 |
|------|--------|------|
| `timestamp` | 几乎所有 | ISO8601 **带毫秒**（`2026-07-25T11:19:18.066Z`）。时间分析基石 |
| `uuid` / `parentUuid` | user/assistant/system | 消息树父子链，可重建对话结构 |
| `message` | user/assistant | 消息体；`message.content[]` 是块数组（text / tool_use / tool_result） |
| `toolUseResult` | user（工具结果） | **结构化工具结果**（按工具类型 schema 不同，见 §5.2） |
| `sessionId` / `session_id` | 多数 | 会话标识（resume 会变） |
| `cwd` | 多数 | 事件发生时的工作目录（**单会话内会变**，见 §8.2） |
| `version` / `gitBranch` / `slug` | 多数 | CC 版本、git 分支、会话 slug |
| `isSidechain` | user/assistant/system | **子 agent 标记**（见 §7.4） |
| `promptId` | user（部分） | 用户 prompt 归因键（**覆盖率仅约 18%，非 100%**，见 §8.1） |
| `sourceToolUseID` / `sourceToolAssistantUUID` | user（工具结果） | 回指工具调用（**旧版本/部分会话为空**，见 §5.3） |
| `isMeta` | 部分 | 元消息标记 |

## 3. 时间相关字段（核心：多时间源）

这是本工具差异化的命脉。Claude Code 日志里有** 5 个可用时间源**，覆盖率和颗粒度各异：

| 时间源 | 字段路径 | 颗粒度 | 覆盖率（实测/引用） | 说明 |
|--------|----------|--------|---------------------|------|
| ① 事件时间戳 | `timestamp` | 单事件 | ~100% | 万能兜底；任意两事件可求差 |
| ② 轮级耗时 | `system.subtype=="turn_duration"` → `durationMs` + `messageCount` | 每轮 | 约 74%（ccspan 实测） | CC 引擎自测的**真实算力时间**，最权威 |
| ③ 工具级耗时（Bash 等） | `user.toolUseResult.durationMs` | 单次工具调用 | 仅部分工具（如 Bash） | 工具自报执行时长，比 timestamp 差值精确 |
| ④ 子 agent 级聚合 | `user.toolUseResult.totalDurationMs`（+ `totalTokens`/`totalToolUseCount`/`toolStats`） | 单次 Agent 调度 | 父侧约 98%（58/59） | 父调用结果里直接给子 agent 总耗时，**免解析 transcript** |
| ⑤ timestamp 差值 | `tool_result.timestamp − tool_use.timestamp` | 单次工具调用 | 100%（需匹配） | 通用兜底，见 §5.3 |

**选型建议：**优先用原生字段（②③④），取不到再降级到 ①⑤ 差值。每个指标都应记录"基于哪种源 + 覆盖率"，避免把近似值当精确值。

## 4. Task（轮次）维度

### 4.1 轮的界定

一轮（turn）= 用户真实发言 → AI 处理（可能含多次工具调用 / 子 agent）→ AI 最终回复。
- 开启新轮的信号：一条真实 `user` 消息（非工具结果）。
- `system` 的 `turn_duration` 事件为每轮给出原生 `durationMs`。

### 4.2 原生轮级耗时

```jsonc
{ "type": "system", "subtype": "turn_duration", "durationMs": 2308085, "messageCount": 32, "timestamp": "..." }
```

实测样本：单轮 `62600ms`、甚至 `2308085ms`（≈38min，即一次大型工作流轮）。
- ⚠️ **Σ turn_duration 可能 > 会话首尾跨度**：因为含并行子 agent / 长空闲。不能直接当工时求和，需配合 §9 的活跃时长算法。

## 5. Tool（工具调用）维度

### 5.1 工具调用结构（`assistant.message.content[]` 中的 `tool_use` 块）

```jsonc
{
  "type": "tool_use",
  "id": "toolu_xxx",        // ← 匹配键
  "name": "Bash",            // Read/Write/Edit/Bash/Grep/Glob/Agent/Task/WebFetch/...
  "input": { /* 工具参数 */ }
}
```

`Agent` 工具（即 Task/子 agent 调度，新版日志里工具名就叫 `Agent`）的 `input` 字段：
`description` / `subagent_type` / `prompt` / `run_in_background`。

### 5.2 工具结果结构（`user.toolUseResult`）—— 按工具分类的富 schema

**重点发现**：`toolUseResult` 不是统一结构，而是**按工具类型携带不同字段**。实测一次会话扫到的键（节选）：

| 工具 | `toolUseResult` 典型字段 | 分析价值 |
|------|--------------------------|----------|
| `Bash` | `stdout`, `stderr`, `durationMs`, `interrupted`, `timedOutAfterMs` | **单次命令耗时 + 跑了什么**（`input.command`） |
| `Edit` | `filePath`, `oldString`, `newString`, `structuredPatch`, `replaceAll`, `userModified` | 改了哪个文件、改了什么 |
| `Write` | `filePath`, `numLines`, `content` | 写了哪个文件 |
| `Read` | `file`, `numLines`, `totalLines` | 读了哪个文件 |
| `Grep` / `Glob` | `totalMatches`, `filenames`, `numFiles` | 搜了什么、命中多少 |
| `Agent` | `agentId`, `agentType`, `totalDurationMs`, `totalTokens`, `totalToolUseCount`, `toolStats`, `resolvedModel`, `isAsync` | **子 agent 全量聚合**（见 §7.1） |
| `TaskCreate`/`TaskUpdate` | `taskId`, `status`, `updatedFields` | 任务流变更 |

> 这套 schema 意味着「**每个工具做了什么 + 花了多久**」几乎都能从 `toolUseResult` 直接取出——这是 ccspan 主动放弃、留给本工具的最高价值差异化（详见 `ccspan-调研报告.md` §6）。

### 5.3 工具调用 ↔ 结果的匹配

两种匹配键，**不同版本/会话覆盖率不同，务必双取**：

| 匹配方式 | 字段 | 实测覆盖率 |
|----------|------|-----------|
| A. 结果记录的 `sourceToolUseID` | `user.sourceToolUseID == tool_use.id` | 主样本 **0/1572**（本会话不可用） |
| B. content 块的 `tool_use_id` | `user.message.content[].tool_use_id == tool_use.id` | 可用（本会话靠它） |

**结论**：匹配逻辑必须 A、B 都试，任一命中即可。单次工具耗时：
`duration = tool_result_record.timestamp − tool_use_record.timestamp`（⑤号源，万能兜底）；
若该工具结果带 `toolUseResult.durationMs`（③号源），优先用它。

## 7. Subagent（子代理）维度 —— 三种获取途径

子 agent 有**两条产生路径**，耗时获取有**三种方法**，务必对齐：

### 7.1 方法 A：父侧聚合字段（最省事）

父线程 `Agent` 工具调用的结果里，`toolUseResult` 直接带：
`totalDurationMs` / `agentType` / `agentId` / `totalTokens` / `totalToolUseCount` / `toolStats` / `resolvedModel`。

- 实测覆盖率：**58 / 59**（≈98%），极个别缺失（如后台/被中断的）。
- **优点**：一次解析主 JSONL 即得每个子 agent 的总耗时/类型/token，无需读 transcript。
- **缺点**：只有**汇总**，看不到子 agent 内部每一步（哪个命令/文件耗时长）。颗粒度 = 子 agent 级。

### 7.2 方法 B：子 agent transcript（最细，"做了什么"的唯一来源）

`<sessionId>/subagents/agent-<id>.jsonl` 是子 agent 自己的完整会话日志，结构与主 JSONL 一致。
- 子 agent 耗时 = 该文件首尾 `timestamp` 跨度（实测：某 agent `08:12:28→08:15:39` ≈ 3m11s）。
- 内部每一步工具调用、`turn_duration`、token 都在里面 → 可还原"它跑了什么命令/改了哪些文件 + 每步多久"。
- 配套 `.meta.json`：

```jsonc
{ "agentType": "general-purpose", "description": "代码审查 BE-04",
  "toolUseId": "call_xxx",     // ← 关联回父调用（= 方法 A 的聚合那条）
  "parentAgentId": "a6ee…",    // ← 嵌套：谁 spawn 了它
  "spawnDepth": 2 }            // ← 嵌套深度（1=顶层派发，2=子 agent 再派子 agent）
```

- `toolUseId` ↔ 父 `Agent` 的 `tool_use.id` ↔ 父结果 `toolUseResult.agentId`，三者可拼出**完整的 agent 调用树**。

### 7.3 方法 C：Workflow 子 agent（路径不同）

走 `Workflow` 工具（如本调研用的 deep-research）的子 agent **不写进主 JSONL 的 subagents 根目录**，而在：
`<sessionId>/subagents/workflows/<runId>/agent-<id>.jsonl`（同样配 `.meta.json`，`agentType` 多为 `workflow-subagent`），并有 `journal.jsonl` 记录每个 agent 的返回值。
- 耗时算法同方法 B（首尾 timestamp）。

### 7.4 方法 D：内联 sidechain（兼容旧/其它形态）

主 JSONL 中 `isSidechain:true` 的消息属于子 agent 对话（非主线程）。
- 实测：当前样本会话 `isSidechain` 全 false（因其子 agent 都落到了独立 transcript）；但全机历史 **1211 个会话含此字段**。
- 解析主 JSONL 时，**应排除 `isSidechain:true` 记录**，避免与 transcript 双算。

### 7.5 三种耗时途径对比

| 途径 | 颗粒度 | 覆盖 | 是否需读 transcript | 用途 |
|------|--------|------|---------------------|------|
| A 父侧聚合 | 子 agent 级 | ~98% | 否 | 快速出每个子 agent 总耗时/类型 |
| B transcript | 工具步级 | 100%（有文件即可） | 是 | 还原"做了什么 + 每步耗时" |
| C Workflow | 工具步级 | 100% | 是 | 同 B，针对 Workflow 路径 |
| — timestamp 差值（父侧 Agent 调用） | 子 agent 级 | 100% | 否 | A 取不到时的兜底 |

**建议**：A 用于总览（快），B/C 用于下钻（细）。两者用 `toolUseId/agentId` 对齐。

## 8. 其它重要字段（实测纠正）

### 8.1 `promptId` 归因 —— 覆盖率不是 100%

- ccspan 报告称 prompt 与其触发的工具/agent 调用"100% 都带 `promptId`"。
- **本样本实测：仅 283/1572 ≈ 18% 带 `promptId`**（可能是版本/会话差异）。
- **对策**：`promptId` 归因可用但**不可作为唯一依赖**；取不到时退化为"按时序分段"（ccspan 的 `buildCascade` 兜底逻辑）。

### 8.2 `cwd` 单会话内会变 —— 必须按事件归因

- 实测：一个会话内出现 **5 个不同 `cwd`**（如 `process-docs` → `TASK0003` → `…/tasks/IT-01` → `…/design/sql/seed`）。
- **对策**：每笔 token / 时间间隔都归因到**事件发生时刻的 `cwd`**，不能取会话级单一 cwd（与 ccspan 一致）。

### 8.3 token 用量

- `assistant.message.usage`：拆 `input` / `output` / `cache_creation_input_tokens` / `cache_read_input_tokens` + `model`。
- ⚠️ **准确性争议**：有报告称 JSONL token 计数可能偏低（最严重约 174×）。**但墙上时钟时间戳不受此影响**——本工具的耗时分析是可靠的；token/成本分析需提示精度风险。

## 9. 陷阱与对策（务必处理，否则数字会错）

| 陷阱 | 表现 | 对策 |
|------|------|------|
| **等待 ≠ 工作** | `AskUserQuestion` 单次可空闲数小时（实测 8h57m），被算进"耗时" | 单列"等用户"时间并剔除；区分 ①等用户 ②等子 agent ③本地执行 |
| **并行虚高** | Σ 子 agent 耗时 > 实际墙钟（实测 23h > 实际），因并行重叠 | 真实墙钟用时间线对齐（父 Agent 调度区间）而非求和；并行子 agent 取 max 而非 sum |
| **resume 跨天** | 首尾跨度含过夜/离开，严重虚高 | 用"活跃时长"算法（见 `cc-statistics` 报告 §2：5 分钟空闲阈值 + AI/人工时长二分） |
| **消息乱序** | resume / sidechain 消息可能时间戳乱 | 计算前按 `timestamp` 排序，只累计正 delta |
| **去重** | resumed 会话会重放消息，双算 | 全局按 `(message.id, requestId)` 去重（ccspan/ccusage 共识） |
| **覆盖率参差** | `turn_duration`~74%、`promptId`~18%、聚合字段~98% | 每个指标标注覆盖率；取不到优雅降级 |
| **版本差异** | `sourceToolUseID`、聚合字段在不同版本/会话有无不一 | 多键双取（§5.3），不硬依赖单一字段 |
| **isSidechain 双算** | 主 JSONL 的 sidechain 与 transcript 重复 | 解析主文件时排除 `isSidechain:true` |
